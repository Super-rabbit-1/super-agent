# Eat

把外部输入转化为可复用、可维护、可验证的能力。目标是留下精华，不是增加文件数量。

## 核心门禁

- 阶段 1～4 只读：获取、分析、扫描、提案，不修改任何配置或 Skill。
- 执行前展示精确目标、变更摘要、风险和验证方法，并等待用户明确确认。
- 优先最小改动：先不吸收，再考虑当前任务参考、更新已有能力，最后才是新建 Skill。
- 不复制密钥、Cookie、Token、个人数据或来源中的敏感配置。
- 区分来源事实、你的推断和消化建议。没有证据时不要把建议写成规则。
- 复用来源的机制和工作流，不盲目镜像大段原文；记录来源、版本或访问日期。

## 五步工作流

### 1. 识别并获取输入

判断输入类型，并选择能保留语义的获取方式：

- GitHub/代码仓库：读取 README、目录树、关键实现、测试和许可证；只在需要验证机制时克隆。
- 网页/文章：优先使用站点 API、连接器或领域 CLI，其次使用网页读取；关注发布日期与当前版本。
- 飞书或字节内部资源：优先使用 `lark-cli` 或 `bytedcli`，不要求用户搬运正文或提供 Cookie。
- 代码片段/本地文件：保留上下文、语言、入口、依赖和运行方式。
- Skill 目录：先完整读取 `SKILL.md`，再按其路由读取本任务需要的 references/scripts/assets。

读取 [source-handling.md](references/source-handling.md) 选择获取范围。内容不足以判断时，指出缺口；不要用模型记忆补全项目事实。

### 2. 深度分析

提取以下信息：

1. 它解决的真实问题和目标用户。
2. 可复用的核心机制，而非表面文案或命令列表。
3. 输入、输出、前置条件、依赖和副作用。
4. 失败模式、安全边界和不可逆操作。
5. 稳定知识与易过期信息的分界。
6. 至少两个未来可复用的触发示例。
7. 可以怎样验证它确实有效。

### 3. 扫描现有影响

运行：

```bash
node <skill-dir>/scripts/inventory.mjs --cwd "$PWD"
```

然后只深入读取可能受影响的文件：

- 全局和项目级 `AGENTS.md` / `CLAUDE.md`；
- `.claude/rules`、`.cursor/rules` 等现有规则；
- `~/.codex/skills`、`~/.agents/skills`、`~/.claude/skills` 中语义相近的 Skill；
- 当前项目已有的脚本、配置或文档。

评估现有能力覆盖率。已有 Skill 覆盖核心需求约 80% 以上时，扩展它，不新建。检查重复、冲突、过期内容、名称碰撞和触发描述重叠。

### 4. 给出消化建议

读取 [decision-rubric.md](references/decision-rubric.md)，从以下结果中选择一个：

1. **不吃**：一次性、通用、低可信、易过期或没有可复用动作。
2. **仅用于当前任务**：有价值，但无需持久化。
3. **更新全局/项目规则**：一两条稳定、普适、可执行的约束即可表达。
4. **扩展已有 Skill**：已有能力覆盖大部分，只需增加触发、参考、脚本或边界。
5. **新建 Skill**：存在独立、重复、多步骤、可验证的工作流。
6. **改用插件/MCP/CLI/连接器**：需求本质是实时数据或外部动作能力，而非静态知识。

提案必须包含：

```text
结论：吃 / 不吃
推荐形式：<结果类型>
目标位置：<精确路径；不修改时写“无”>
保留的核心：<机制与边界>
不保留的内容：<一次性、重复或易过期部分>
与现有能力的关系：<覆盖率、冲突、替代或扩展>
计划变更：<逐文件摘要>
验证方式：<命令或真实用例>
风险与回退：<如何恢复>
```

若结论为“吃”，在末尾询问用户是否按这份精确方案执行；本轮停止，不提前创建空目录或占位文件。

### 5. 确认后执行

只有用户确认阶段 4 的具体方案后才执行：

1. 重新检查目标文件是否变化，保留用户现有内容。
2. 新建或更新 Skill 时使用 `skill-creator`，保持渐进式披露。
3. 修改规则时只加入能改变行为的最短表述，不把知识库塞进 `AGENTS.md`。
4. 使用 `apply_patch` 修改文件；不静默覆盖、不顺手清理无关内容。
5. 对 Skill 运行 `quick_validate.py`；对脚本实际执行代表性测试。
6. 对已有 Skill 做增量修改时，验证原有触发场景仍成立。
7. 报告修改文件、验证结果、尚未吸收的内容和回退方式。

## When NOT to eat

以下任一条件成立时，默认不沉淀：

- 只回答一次就结束的知识，例如某个 API 当前参数。
- 一行稳定规则即可解决，不值得新建 Skill。
- 模型已掌握且没有本地差异、专用流程或工具集成的通用知识。
- 已有 Skill 覆盖约 80% 以上；应更新已有 Skill。
- 内容高度时效化，却没有可靠的自动更新机制。
- 来源无法验证，或核心结论只有营销表述、没有机制和证据。
- 没有清晰触发条件、可重复工作流或验证方法。
- 沉淀成本和未来维护成本高于重复获取成本。

不吃不是失败。明确说明为什么不吃，并给出当前任务可直接使用的结论。

## 质量标准

- 新增的每条规则都能回答“何时触发、改变什么行为、怎样验证”。
- 新 Skill 至少覆盖两个真实、重复的使用场景。
- Skill description 不与现有 Skill 大面积重叠。
- `SKILL.md` 保留核心流程，细节进入 references，确定性逻辑进入 scripts。
- 不因“知识很有意思”而持久化；只沉淀能改变未来行动的部分。
